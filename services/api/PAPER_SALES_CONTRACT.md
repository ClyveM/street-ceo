# Daily sales sheets — HTTP contract (PAPER-DAILY-API-001)

Base `/api/v1/shops/{shop_id}`, matching `X-Shop-ID` mandatory. Today's open shop-local business day only. Existing customer receipts remain unchanged. All returned sheet records have `record_type: daily_sales_batch` and `status: draft|reviewed|confirmed`.

- POST `/daily-sales-batches/extract`, multipart `image` PNG/JPEG/WebP <=5 MiB, client deadline >=35 seconds. Returns persistent PaperSalesRecord draft, `business_date` today, image SHA256, filename/content_type/source_ref, OCR line candidates/warnings/extraction_status and existing day sales/counts. Unavailable OCR yields an honest empty editable draft; no invented extraction or stock changes.
- POST `/daily-sales-batches/{id}/review`, JSON `{business_date,actor,source_ref,notes,lines:[{product_id,quantity,unit_price_cents,line_total_cents}],cash_cents,bank_cents}`. Positive whole qty, nonnegative actual price/amount in integer cents, qty*price=amount, unique <=100 products, sum line amounts=cash+bank. All required; unknown tender must be resolved, never defaulted. Returns status reviewed, exact total, saved product_name/sku, stock_baseline, reviewed_version and latest existing day totals. No stock mutation. Current catalogue prices are not accepted automatically.
- POST `/daily-sales-batches/{id}/confirm`, JSON `{reviewed_version,confirmed:true,only_unrecorded:true,prices_reviewed:true,stock_not_reflected:true}`, `Idempotency-Key` required. All declarations explicit. Revalidates day/open/count/stock/day-evidence baseline and duplicate source/canonical content; atomically records batch+stock+audit. Exact retry returns original; changed request under same key409. Cash+bank allocation records payment, never tendered/change/verified settlement. Historical COGS unknown.
- GET `/daily-sales-batches` list newest created first, GET `/{id}` exact persisted draft/reviewed/confirmed recovery, GET `/{id}/image` private scoped source bytes. Confirmed record immutable. GET does not post/re-confirm anything.

PaperSalesRecord includes `id,shop_id,record_type,status,business_date,created_at,confirmed_at,filename,content_type,source_sha256,source_ref,ocr_lines,warnings,extraction_status,lines,cash_cents,bank_cents,total_cents,actor,notes,reviewed_version,stock_baseline,existing_sales_total_cents,existing_transaction_count,existing_daily_summary_count,canonical_sha256`. OCR candidates use nullable product_id/quantity/unit_price_cents/line_total_cents and raw_label; reviewed lines require exact values plus saved product_name/sku.

Reports summary/daily/monthly and Today add `daily_summary_count`. Batch gross sales/payment/product quantities included exactly once, while customer transaction_count excludes sheets. Batch unknown COGS propagates unknown product/summary profit; separate missing_cogs_daily_summary_count. History exposes a separate typed collection, never fake Sale/customer receipt. Cash-close includes recorded cash allocation exactly once. Today/AskMuse use same report evidence. No unallocated batch proceeds permitted in this demo. Same canonical reviewed content on another image is blocked; legitimate identical additive batches need a later explicitly reviewed override design.

Product images: preserve existing GET `/products/{id}/image` metadata. Add GET `/product-images` latest metadata per current product and GET `/products/{id}/image/content` private binary with correct MIME and no-store headers, matching X-Shop-ID. Existing metadata's memory backend/ref strings remain legacy compatible; actual bytes are durable in selected SQLite storage. No public filesystem URL.

## Final clarifications
Reviewed `unit_price_cents` is nullable/optional: an exact reviewed `line_total_cents` is authoritative for a combined quantity sold at mixed prices (e.g. three units for 100 cents). If a unit price is supplied, its quantity multiplication must agree exactly; never derive/round a false unit price. Canonical duplicate detection compares business date + sorted product IDs/quantities/line revenue, independent of photo cropping, optional unit price, actor, notes or tender reallocation. Identical additive batches need a future explicit reviewed override; the demo blocks them.

OCR extraction participates in correlated persistent Muse investigations and terminal logging, while raw multipart image data is explicitly excluded from request logging. Scoped source images stay in SQLite assets and are retrieved only through the authenticated-by-shop-scope image route. Customer transactions, amount tendered and change are never invented for a daily sheet.

Product image binary exposes ETag SHA256 and X-Product-Image-ID through CORS so clients can detect an index/content replacement race. Use private, no-store responses and keep names/qty/prices usable when images are missing.

Retention QA followup: exact `remove this item` or `remove item` deliberately removes only the active pending slot. Remaining pending items are still asked; if none remain, the complete retained basket still requires explicit Yes. Removing the only remaining basket item produces an honest non-actionable empty-basket rejection. No generic skip is inferred. Trailing and/plus replies preserve unresolved context, and known missing-quantity targets retain name/SKU stale guards.

## PAPER-REVIEW-STALE-CODE-001
Confirmation returns HTTP409 with `detail: {code: "paper_review_stale", message: string}` only when the requested reviewed_version is stale or the revalidated stock/day-activity baseline differs, before any confirmation mutation. Already-confirmed/not-reviewed status, authorization, missing declarations, idempotency mismatch, date/count/stock-validation and other errors retain their existing distinct errors. Successful exact Idempotency-Key replay is checked first and still returns the original confirmed record even after stock changed.
A client recovering an uncertain original confirmation may offer explicit Review again on the SAME batch only after the original-key retry returns this exact code AND a fresh scoped GET confirms the same batch is not confirmed. Do not unlock solely from GET or arbitrary409/4xx/network failure. Re-review must refresh the persisted version/baseline and acknowledgements; the old pending key is safely retired and a subsequent reviewed confirmation uses a new key. Never create a replacement batch to escape uncertainty.
